# OpenCDR engine operator walkthrough

This is the canonical entry point for operating standalone Core and organization-local
Fleet with the installed Deploy CLI. Web/mobile setup, hosted workers and application
migration are deferred to P10. They are not prerequisites for these engine procedures.

**Handoff status, 2026-11-11:** P0–P7 isolated engine acceptance is complete.
The [12 November handoff guide](handoff-2026-11-12.md) provides the exact local
candidate kit, offline installation, sequential checks and owner worksheet.
The owner deferred the100000-record/10-reader stress test; no quota increase is
required for that bounded handoff. Public artifacts and installed published-version
acceptance remain separate P8 release gates. Owner acceptance remains `not_run`
until the independent operator records it. These documents do not publish a release.

For a new customer account, first follow [fresh-client prerequisites and artifact
bootstrap](fresh-client-installation.md). Do not assume the dated kit's existing
buckets or workstation profiles are available.

## Prepare the workstation and record identities

Use a Python version supported by the selected bundle and AWS CLI v2. The dated
12 November offline bundle is verified for CPython3.14 on macOS arm64. Prebuilt releases do not require a source
checkout, Node, Docker or Serverless. Keep a dedicated working directory for plans,
receipts, manifests and redacted evidence. Set restrictive file permissions with
`umask 077`; do not put AWS credentials in connection JSON.

Obtain an approved bundle containing a pinned Deploy wheel, its dependency lock with
hashes, Core and optional Fleet release directories, their manifest hashes, and a
compatibility record. Each release directory contains `release.json`, `template.json`
and `runtime.zip`. Obtain expected hashes through the reviewed release channel.
A matching SHA proves integrity against that pin, not an independent publisher signature.

```sh
python3 -m venv ./tools
. ./tools/bin/activate
python -m pip install --require-hashes -r deploy-install.lock
opencdr-deploy --version
python -m pip check
aws sts get-caller-identity --profile "$CORE_PROFILE" --query Account --output text
aws sts get-caller-identity --profile "$FLEET_PROFILE" --query Account --output text
```

The lock file is a release input, not generated by this command. Omit the Fleet identity
check for standalone mode. Compare returned accounts to the approved account/region/stage
worksheet before any change. Refresh SSO using `aws sso login --profile PROFILE` if needed.
Stop on identity, artifact or dependency mismatch. Never fall back to `latest`.

Deployment and operator identities are different. The deployment profile needs the
permissions declared by the selected templates, artifact-bucket access and scoped
`iam:PassRole`. API callers use the relevant IAM observer, triage, operator, responder,
administrator, integration or delivery endpoint. An application role is not an AWS grant.
Use least-privilege operator connections for ordinary reads; keep administration separate.

## Check regional execution capacity

Before concurrent acceptance, record the applied regional quota and the other stacks
sharing that account. Function count is not execution capacity: each simultaneous
invocation consumes capacity, and scheduled/background workers need headroom too.

```sh
aws lambda get-account-settings --profile "$FLEET_PROFILE" --region "$REGION" \
  --query 'AccountLimit.{Concurrent:ConcurrentExecutions,Unreserved:UnreservedConcurrentExecutions}'
aws service-quotas get-service-quota --profile "$FLEET_PROFILE" --region "$REGION" \
  --service-code lambda --quota-code L-B99A9384
```

Repeat for the Core profile when testing standalone capacity. For the12 November
handoff, use one foreground request at a time. The owner explicitly deferred the
10-reader stress workload and its associated quota increase on2026-11-11. Keep
that prior failed run as evidence; neither cleanup nor this deferral passes it.
Other baseline, delivery, retention, security and recovery requirements remain.
Do not stop production workers or request a larger quota as part of this handoff.
If a sequential check throttles, record the failure and reconcile the affected
operation. Resuming the original stress gate requires a separately scheduled run.

Reconcile `AWS/Lambda` `Throttles`, `Errors` and `Invocations` with API errors for the
same minute-aligned window. An API 5xx can precede a Lambda invocation; absence of a
function error log does not make the request successful. Keep failed runs. Read-only
checks may be repeated after a verified correction; reconcile a mutation's request ID
and durable receipt before considering a retry.

## Install standalone Core

1. Set `CORE_PROFILE`, `CORE_ACCOUNT`, `REGION`, `CORE_STAGE`, `CORE_MANIFEST_SHA256`
   and `ARTIFACT_BUCKET` to reviewed values. Use a new isolated stage for acceptance.
2. Verify the release before AWS writes:

```sh
opencdr-deploy release verify ./core-release --sha256 "$CORE_MANIFEST_SHA256"
opencdr-deploy release flags ./core-release --sha256 "$CORE_MANIFEST_SHA256"
```

3. If no suitable artifact bucket exists, use `release bootstrap` and review/execute
   its returned change set as documented in [prebuilt releases](prebuilt-releases.md).
   Wait for that stack's `CREATE_COMPLETE`. Reuse the bucket on later upgrades.
4. Prepare a change set; this uploads immutable artifacts but does not execute it:

```sh
opencdr-deploy release plan ./core-release --sha256 "$CORE_MANIFEST_SHA256" \
  --profile "$CORE_PROFILE" --account-id "$CORE_ACCOUNT" --region "$REGION" \
  --stage "$CORE_STAGE" --artifact-bucket "$ARTIFACT_BUCKET" > core-plan.json
```

5. Review the exact account, region, stack, template, permissions, feature parameters,
   replacements/deletions and retained storage. Record the returned change-set ARN.
   Then execute only that reviewed ARN:

```sh
opencdr-deploy release execute "$CORE_CHANGE_SET_ARN" --profile "$CORE_PROFILE" \
  --account-id "$CORE_ACCOUNT" --region "$REGION"
aws cloudformation describe-stacks --profile "$CORE_PROFILE" --region "$REGION" \
  --stack-name "opencdr-$CORE_STAGE" --query 'Stacks[0].[StackStatus,ChangeSetId,Outputs]'
```

6. Poll stack state with a bounded 30-minute installation window. Successful CLI
   submission is not completion. Require `CREATE_COMPLETE` or `UPDATE_COMPLETE`,
   the reviewed change-set identity, expected runtime hashes and healthy mappings.
   A timeout is an unknown outcome: inspect the same stack before retrying.
7. Complete [detection activation](detection-activation.md): wait the required
   post-update drain, run a fresh retained-source backfill, inspect findings, prepare
   and apply the exact activation plan. Do not remove a barrier or reset a consumer.
   A completed scan does not prove complete historical coverage.
8. Use the endpoint in the verified stack outputs to create an IAM connection:

```sh
opencdr-deploy release connection ./core-observer.json --url "$CORE_URL" \
  --profile "$CORE_OBSERVER_PROFILE" --account-id "$CORE_ACCOUNT" \
  --region "$REGION" --stage "$CORE_STAGE" --access observer
opencdr-deploy api request GET /status --connection ./core-observer.json
```

Require matching deployment identity and advertised capabilities. HTTP 503
`detection_activation_required` means the activation gate is still closed.

## Add Fleet for multiple accounts

For a new multi-account installation, install Fleet paused first, verify its exact
role outputs, then install/activate Core members with that reviewed trust. For
existing Core members, review the trust/ownership transition separately. Verify
the Fleet account; never infer authorization from a stage name. Obtain the compatible
Fleet bundle, manifest hash, security-account profile and registration inputs.

```sh
opencdr-deploy release verify ./fleet-release --sha256 "$FLEET_MANIFEST_SHA256"
opencdr-deploy release plan ./fleet-release --sha256 "$FLEET_MANIFEST_SHA256" \
  --profile "$FLEET_PROFILE" --account-id "$FLEET_ACCOUNT" --region "$REGION" \
  --stage "$FLEET_STAGE" --artifact-bucket "$FLEET_ARTIFACT_BUCKET" \
  --pause-detection-polling > fleet-plan.json
opencdr-deploy release execute "$FLEET_CHANGE_SET_ARN" --profile "$FLEET_PROFILE" \
  --account-id "$FLEET_ACCOUNT" --region "$REGION"
opencdr-deploy fleet connect acceptance --url "$FLEET_URL" --profile "$FLEET_PROFILE" \
  --security-account-id "$FLEET_ACCOUNT" --region "$REGION" --stage "$FLEET_STAGE"
opencdr-deploy fleet status --fleet acceptance
opencdr-deploy fleet agents list --fleet acceptance
```

Execute only after reviewing the returned plan. Wait for stack completion before
connecting. Register members using the pinned Fleet API schema and exact Core identity,
URL and IAM role. Read back each registration and revision. Keep writes disabled until
their specific operations and target scopes have been reviewed. Registration does not
transfer case or Library ownership.

Health/configuration polling and detection polling are separate. After Core activation,
verify each delivery subscription/generation and then prepare one reviewed Fleet release
plan with `--enable-detection-polling`. Preserve existing consumers and pending receipts.
Inspect `/v1/agents/AGENT/detections/status` until its checkpoint catches up; record the
actual observation time, generation and lag. Do not treat a manual queue wake-up as a
normal-schedule performance result. See [Fleet acceptance](../../opencdr-fleet-manager/docs/acceptance.md).

## Cases, Library, reviewed changes and automation

Use [owner workflows](owner-workflows.md) for grants, policy, reviews and receipt checks,
and [owner automation](owner-automation.md) for routing and durable delivery. Preserve
request IDs and expected revisions. Read a receipt after an uncertain response before
considering another write. Never create a new request ID to evade an uncertain effect.

- Case scope is an explicit owner-local grant. Temporarily granted fixture access must
  be restored with revision checks after acceptance.
- Library imports create immutable authoring versions. Imported provider history is
  inert; neither import nor preview activates rules or dispatches a response.
- Reviewed distribution freezes membership and records each target's independent result.
  Logical target simulation is not proof of deployment to that many real accounts.
- `sending`/unknown external-effect claims remain non-retryable until reconciliation.
  A stored worker result is not independent proof of a provider effect.
- Routing requires a customer-runner wake-up. The portable runner is not an installed
  production scheduler. Keep test policies disabled after the drill.
- Subscription initialization is create-only. ACK only after the sink durably commits
  the exact page. Checkpoint reset is not a catch-up strategy.

The portable MCP client can use the same secret-free IAM connection when its pinned
compatibility record permits it. Hosted assistant/MCP endpoints remain P10. Configure
external notification/SIEM destinations only under a separately authorized integration
procedure; this isolated engine acceptance sends no provider notifications.

## Upgrade, restore and ownership changes

Use [detection activation](detection-activation.md) to pause Core reads before a runtime
upgrade. Review one substantial release batch, execute it, wait for stack completion
and the documented drain, run a new backfill and activate the verified generation.
Reconcile Fleet consumption afterward. Retain all original plans and receipts.

Physical restore uses `release storage-recovery`; see
[Fleet storage recovery](fleet-storage-recovery.md) for its fenced plan/capture/restore/
bind/verify/resume sequence. Pass each exact file and SHA. Failed stacks remain fenced
until the recovery controller completes. Do not roll them back or manually remove leases.
If a planner loses its response, reconcile its saved request identity against AWS first.

**P7 native engine ownership transfer and reverse recovery are accepted for the
isolated scope.** Follow [ownership transfer](ownership-transfer.md) using new
reviewed plans, exact physical/runtime pins and an empty initial destination family.
The live rehearsal preserved post-cutover writes, history, evidence and portable
consumers, verified cancellation, and recovered retained archives byte-for-byte.
Application/SaaS migration remains P10. Do not reuse completed plans from retired
test stages or delete retained data to create an empty destination.

## Measurements and handoff

Complete the [engine acceptance worksheet](engine-acceptance-worksheet.json) and use the
[KPI guide](engine-kpis.md). Record exact artifacts, scope, sample sizes, cold/warm behavior,
raw measurements and limitations. Existing engineering evidence is not the owner's run.
An unmeasured metric is `not_run`; a partial cost subtotal is not a passed cost gate.

Finish each fixture by disabling test policies/bindings, restoring scopes/grants,
closing test cases, verifying absence of disposable roles/resources, and retaining
immutable history. Never delete shared data to make a cleanup check pass.

| Failure | Required next action |
| --- | --- |
| Hash/version/capability mismatch | Stop and obtain the exact compatible bundle. |
| Expired SSO | Refresh that profile, then recheck account identity. |
| Access denied | Record the operation/resource; correct the scoped grant. |
| Stale revision | Read current state and reconcile the original request. |
| Timeout or lost response | Read the same receipt/change set; do not blindly resubmit. |
| Failed CloudFormation or held recovery lease | Use the pinned recovery controller and retained plan. |
| Missing telemetry | Record `not_run`; establish counters before a new sample. |
| Wrong account or unexpected replacement | Do not execute the plan. |

Owner sign-off must contain the owner's independent deployment/test result. Until it
arrives, report engineering readiness and owner acceptance as separate statuses.
